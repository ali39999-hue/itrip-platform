# سند جامع معماری امنیت فیروزه (Firuzo / iTrip Security Architecture Specification)
> **استاندارد:** انطباق با OWASP ASVS 5.0 (سطح ۲ و ۳) + استانداردهای امنیتی رزرواسیون گردشگری و فین‌تک  
> **وضعیت:** سند مرجع مهندسی امنیت (Security Engineering Program - SEP)  
> **نسخه:** ۲.۰.۰ — ۲۰۲۶-۰۹-۱۱  

---

## ۱. چشم‌انداز برنامه مهندسی امنیت فیروزه (Executive Overview)

پلتفرم **فیروزه (iTrip)** به عنوان یک سوپراپ گردشگری یکپارچه (OTA + ERP + B2B + FinTech)، نقطه تلاقی داده‌های حساس هویتی مسافران، تبادلات مالی چند ارزی، و پروتکل‌های رزرو متصل به تأمین‌کنندگان مختلف (Alibaba, FlyToday, Parto CRS, Eghamat24 و خطوط هوایی) است.

امنیت در فیروزه یک اسکنر مقطعی نیست، بلکه یک **چرخه پیوسته (Security Engineering Program)** در سراسر لایه‌هاست:

```
[ کد و تست امن ] ──> [ پایپ‌لاین CI/CD ] ──> [ معماری کانتینر ] ──> [ گیت‌های ران‌تایم و WAF ] ──> [ مانیتورینگ و لاگ محافظت‌شده ]
```

## ۳. قواعد شکست‌ناپذیر بیزینس سفر و فین‌تک (Travel Invariants)

### ۳.۱. چرخه تراکنش‌های مالی و کیف پول (Wallet & FinTech)
1. **اصل تغییرناپذیری دفترکل (Append-Only Immutable Ledger):**
   - بالانس هیچ حسابی مستقیماً با مقدار عددی بازنویسی نمی‌شود. هر افزایش یا کاهش، نتیجه درج یک سند تراکنش متوازن با طرف بدهکار و بستانکار است.
2. **پیشگیری از اضافه برداشت همزمان (Pessimistic Row Locking):**
   - در زمان کسر موجودی، رکورد والت با فرمان `SELECT id FROM "Account" WHERE id = $1 FOR UPDATE` قفل می‌شود تا هرگونه حمله همزمانی (Race Condition) خنثی گردد.
3. **کلیدهای یکتایی و وب‌هوک‌های تسویه (Idempotency & IPN):**
   - تمامی کال‌بک‌های پرداخت و متدهای حساس ثبت سفارش ملزم به ارائه شناسه یکتا (`Idempotency-Key`) هستند.
   - تنها مرجع قطعی تغییر وضعیت پرداخت به `PAID`، وب‌هوک سرور-به-سرور (IPN) امضاشده با HMAC-SHA256 است؛ بازگشت کاربر از درگاه صرفاً یک ریدایرکت رابط کاربری (UX) محسوب می‌شود.

### ۳.۲. یکپارچگی رزرواسیون و نرخ‌ها (Booking & Supplier Engine)
1. **استعلام مجدد اجباری نرخ و ظرفیت (Offer Re-verification Gate):**
   - با توجه به نوسان ثانیه‌ای پروازها و اتاق‌های هتل، پیش از صدور فاکتور نهایی و انتقال کاربر به درگاه بانکی، موتور رزرو موظف است نرخ و ظرفیت زنده را از سرویس‌دهنده بالادستی استعلام کند.
2. **قفل زمانی ظرفیت (Hold & Compensation Rollback):**
   - در صورت شکست مرحله نهایی یا انقضای زمان پرداخت (معمولاً ۱۵ دقیقه)، سهمیه نگه داشته شده در سیستم تأمین‌کننده باید فوراً آزاد (Release) شود.
3. **تفکیک کامل مستأجرها در B2B (Multi-Tenant Isolation):**
   - دسترسی آژانس‌های همکار (B2B Tenants) کاملاً مبتنی بر `organizationId` ایزوله بوده و مشاهده اطلاعات مسافران، کمیسیون‌ها و تراکنش‌های آژانس دیگر تحت هیچ شرایطی امکان‌پذیر نیست.

## ۴. چرخه احراز هویت و مدیریت سشن‌ها (Auth & Session Security)

1. **مدیریت کوکی‌ها (Cookie Hygiene):**
   - کوکی‌های سشن دارای فلگ‌های `HttpOnly=true`، `Secure=true` و `SameSite=Lax` هستند.
   - هیچ توکن اعتبارسنجی دسترسی یا کلید احراز هویت در `localStorage` یا `sessionStorage` ذخیره نمی‌شود.
2. **چرخش و باطل‌سازی سشن (Session Invalidation):**
   - در صورت تغییر کلمه عبور یا خروج کاربر، تمام سشن‌های فعال قبلی بی‌درنگ در پایگاه داده یا استور ریدیس منقضی می‌شوند.
3. **کنترل نشت در آدرس‌ها (No Sensitive Data in URLs):**
   - طبق الزام صریح ASVS 5.0، هیچ فیلد هویتی، کلمه عبور، کد OTP، توکن ریست، شماره شبا یا فیش واریزی نباید در URL و Query Parameter قرار گیرد.

## ۵. امنیت زنجیره ابزار و گیت‌های CI/CD (DevSecOps Pipeline)

برای اطمینان از حفظ وضعیت ایمن در هر پول‌ریکوئست (PR)، زنجیره ارزیابی زیر اجرا می‌شود:

```bash
# گیت ۱: اعتبارسنجی استاتیک و تایپ‌ها
npm run typecheck

# گیت ۲: تست‌های یکپارچگی واحد، مالی و دامنه‌ای
npm run test:unit

# گیت ۳: اسکن آسیب‌پذیری وابستگی‌ها، کانتینر و بررسی کلیدها
npm run security:scan

# گیت ۴: گیت دسترسی‌پذیری و بومی‌سازی کامل
npm run gate:a11y && npm run gate:i18n

# گیت ۵: ممانعت از ارسال دمو مود به تولید (CI-012)
npm run build
```

## ۶. پروتکل واکنش به رخدادهای امنیتی (Incident Response Playbook)

1. **کشف نشت کلید یا توکن:**
   - باطل‌سازی فوری کلید در سرور تأمین‌کننده / کنسول درگاه.
   - استقرار کلید جدید رمزنگاری‌شده در متغیرهای محیطی با ری‌استارت امن کانتینرها.
2. **حمله Brute-force یا DoS روی اندپوینت‌های حساس (OTP/Search):**
   - فعال‌سازی خودکار لایه مسدودسازی در `redis-rate-limiter.ts` و برگرداندن پاسخ `429 Too Many Requests`.
3. **سوءاستفاده مالی یا خطای ناهمخوانی دفترکل:**
   - مسدودسازی خودکار تراکنش با ایجاد فلگ `RECONCILIATION_REQUIRED` و ارسال هشدار فوری به کارتابل ناظر ارشد مالی.
